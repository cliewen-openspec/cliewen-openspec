# Cliewen for OpenSpec 0.2.0

Version 0.2.0 adds guidance for scoping work, investigating uncertainty, and preserving useful project knowledge. Follow [your first change](../guide/getting-started.md) for a complete worked example.

## Plan the next useful change

Agents assess whether work needs an OpenSpec change, split oversized proposals, and prepare detailed proposals when the work becomes actionable. Upcoming work uses your existing ticket system or a lightweight local plan. Ticket access uses tools exposed by the agent host and your authorization.

When consequential uncertainty needs an experiment, the agent can suggest a bounded prototype. You choose whether to run it. Findings, feedback, uncertainty, and prototype cleanup stay with the investigation.

Optional product intent and cross-capability journeys help detect drift and scope creep. They reference behavioral specs and reuse existing project records. Routine tasks require no new goal, journey, or prototype.

## Automate checks and keep decisions understandable

Before requesting manual work, agents assess what available authorized tools can automate and explain any remaining need for judgment, access, or authority. Human observations retain who checked what, the tested version, conditions, results, and limits. Feedback does not imply release authorization.

Shared writing guidance asks agents to make proposals and handoffs understandable without the project conversation, link detailed requirements, and use diagrams when clearer. These are agent instructions; automatic checks do not establish readability or assertion sufficiency.

## Preserve useful knowledge around archive

Closure guidance brings together affected documentation, decisions, test maintenance, and enabled learnings. Projects can expose it to a separate archive session through OpenSpec's optional operation guidance. After archive, agents reassess future work against actual results.

OpenSpec continues to own synchronization and archive. Direct CLI archive does not execute Cliewen's review instructions. Project policy still governs Git integration and approval. See [closure setup](../guide/workflow.md#close-the-change-and-preserve-useful-knowledge).

## Upgrade and compatibility

The release extends the existing `cliewen-delivery`, `cliewen-discovery`, and `cliewen-all` schemas. It adds no selectable schema, configuration field, or execution-report format. Existing feature settings continue to apply independently.

Init and update check Node 20.19+ and OpenSpec 1.15.0+ before writes, including previews. A selected broken or incompatible project-local OpenSpec blocks the operation; Cliewen does not upgrade OpenSpec automatically. The documented OpenSpec 1.17.0 npm installation itself needs Node 22.12+.

Resource upgrades from published 0.1.0 preserve project configuration, documents, changes, and acceptance identities. Previews show versions, detected tools, and files to create, replace, or delete. Conflicting local resource edits still require review. Earlier alpha installations and unknown versions remain unsupported; this is not a general project-content migration.

Use the [update guide](../guide/updating.md) for the current local-tarball commands. Registry users can install `cliewen-openspec@0.2.0`, then run `cliewen-openspec update --dry-run --json` before applying `cliewen-openspec update --json`. Installing the npm dependency and refreshing installed resources are separate operations.

The [changelog](../../CHANGELOG.md) lists adopter-visible changes. The [guide philosophy](../guide/index.md#philosophy) explains the shared approach and when to choose each schema.
