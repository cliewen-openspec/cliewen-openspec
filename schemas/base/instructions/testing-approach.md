Use spec-driven development with evidence-first verification.
Before implementation, describe acceptance criteria, relevant positive/negative/boundary cases, and the observations needed for acceptance. Refine this plan when new information changes the requirements.
Plan relevant interactions between supported input content, option states, boundaries, and execution paths. For preservation claims, assert exact content across relevant default, disabled, and enabled paths using inputs that could expose unintended transformation. Select combinations by behavioral risk and record relevant untested combinations; exhaustive combinations are not required. Separate tests of each dimension do not establish their interactions.
Develop and verify small tasks. Test code may be written before, alongside, or after production code. Give each task concrete tests, commands, and a completion check; inspect actual results before proceeding. Documentation-only tasks use suitable validation.
Review assertions against specifications independently of implementation assumptions. Check effectiveness with relevant controlled faults or observed behavior failures where useful; syntax, setup, and unrelated failures are not effectiveness evidence.
Maintain tests as accepted behavior changes. Preserve shared active obligations and retire assertions only after explicit criterion retirement. Keep actual observations and limitations; never invent results.
Read testing.quality.coverage.mode, testing.quality.effectiveness.mode, and testing.lifecycle.mode independently (each defaults to review). Off skips that policy; review requests assessments and warns; enforce requires complete records and execution evidence. Follow the installed package's docs/testing/test-quality.md for formats and limits.
In review mode, disclose unresolved case/record warnings and their impact in the handoff; zero warnings is not a completion requirement. Do not disable policies or invent behavior/cases to silence findings. Enforce mode requires resolving its blocking findings. Execution failures remain blocking in either mode.
When coverage is active, tag Node cases with [Case: kebab-case-id] and [Coverage: positive|negative|boundary], retaining AC and Test-type tags. Use meaningful distinct cases and scoped reviewed exceptions where appropriate; counts do not prove assertion quality.
When effectiveness is active, inspect assertions and record relevant controlled-fault or observed behavior failures. Fix setup or unrelated failures before making effectiveness claims. Do not claim recorded status authenticates approval.
Choose faults that exercise the claimed input and execution path. Credit only the cases and assertions that actually detect the fault; passing another option state or stopping at an earlier assertion does not establish detection elsewhere.
When lifecycle is active, review affected criteria and tests against a baseline. Retain valid behavior assertions through refactoring, update accepted behavior changes, and remove obsolete assertions only after explicit accepted retirement. Preserve shared active obligations and reserved IDs. Author fresh scoped review records, commit reviewed inputs, collect final evidence, and refresh the permanent-spec review after archive. Discovery-only and genuine no-delivery changes need no product-quality records.
Finish documentation and task notes, commit reviewed inputs, then collect revision-bound evidence and run check. Later commits require fresh evidence.
