# Keep changes connected to the user's outcome

Use relevant agreed product context during scoping, design, investigation, review, and closure. Keep the explanation proportional to the decision. Routine understood work needs no new goal, journey, interview, approval step, or explanation for skipping them.

## Reuse the intent

Look first at relevant context already supplied or available in the project's authoritative product brief, README, documents, or selected planning authority. Link to the existing source instead of copying its facts or status. Preserve paths, identifiers, and lifecycle meanings. Resolve learning policy before broader context collection as described in .cliewen-openspec/planning.md.

Use the known audience, problem, desired outcome, constraints, and supported success signals needed for this change. Keep missing intent or metrics unknown; do not invent accepted goals, numerical targets, or user research from implementation details. Clarify consequential missing information through existing project authority. A qualitative goal does not require a fabricated metric.

## Explain a journey only when it helps

For consequential work across capabilities, describe the actor's starting need, relevant steps and handoffs, meaningful failure/recovery paths, and intended outcome. Use a short explanation with a diagram when it makes the path clearer; a table or prose can suffice. Do not require a complete product map, separate goal file, or journey ID.

Link behavioral rules to authoritative OpenSpec specs with descriptive titles and, when useful, exact scenario IDs alongside their meaning. Do not copy the rules into the journey, allocate parallel acceptance IDs, or use a journey as product execution evidence. Label aspirational steps and identify missing or contradictory spec behavior for normal change assessment. A desired recovery step does not establish that it exists.

## Detect drift and scope creep

Compare consequential emerging work with the agreed problem, user outcome, and delivery scope. Surface an approach that no longer serves that outcome; do not rewrite the goal to justify work that has drifted.

Distinguish a necessary in-scope correction from an additional wish. An idea can support the product goal while remaining outside this delivery. Use existing work-scoping rules to retain deferred work in the selected authority when features.planning is enabled and obtain direction before materially expanding agreed scope. With planning disabled, report the additional scope in the current handoff without creating a backlog. A goal or journey does not authorize extra work. Ordinary authorized implementation choices proceed independently with relevant verification.

## Respect settings and preserve useful knowledge

With features.documentation enabled, create or maintain a durable intent/journey explanation only when useful, using configured docsRoot or existing project locations and conventions. Keep each fact in one authoritative home and link to it. Existing records may be sufficient. Without an existing convention, optional examples include product-intent.md and journeys/<name>.md under docsRoot; installation creates neither.

With features.documentation disabled, add no optional intent/journey creation or maintenance requests and preserve authored files. Relevant context already supplied can still inform ordinary scoping and native behavioral specs. Ticket discovery, access, and plan updates independently follow features.planning and the existing planning reference; documentation guidance does not enable ticket access when planning is disabled. Report unavailable external context and pending authorized updates honestly, without inventing their contents or claiming updates succeeded.

Before archive, reconcile only affected explanations with the actual delivery under the enabled settings. Preserve unresolved/deferred work at its existing authority. Follow .cliewen-openspec/closure.md for native archive and moved-link maintenance.

Keep desired outcomes, implemented behavior, and actual observations distinct. Passing capability tests, a completed diagram, and archive alone do not prove user success or human approval. State when no actual user feedback was collected; label illustrative feedback and proposed outcomes. Discovery and combined no-delivery findings require no fabricated product evidence or delivery proposal. Reuse existing project approval and evidence boundaries.
