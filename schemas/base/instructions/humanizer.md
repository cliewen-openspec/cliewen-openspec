Read writing.humanizer (default auto; values auto, on, off). With off, Cliewen requests no skill discovery, use, installation suggestion, or Humanizer status; baseline writing rules and independent host mandates still apply.
With auto or on, inspect the host's exposed skills/capabilities for a usable Humanizer skill, including namespaced forms. Read and apply its instructions before claiming use. A listing or file alone does not prove invocation is permitted. Do not scan global directories or infer absence when inventory is unavailable.
A failed load of a guessed skill name without an inventory entry establishes neither detection nor absence. Report availability unknown and describe the failed invocation separately; reserve detected but inaccessible for a skill the host actually identifies. Do not combine these states into an ambiguous status.
When first handling prose under this policy, give the user one brief status per session: actually used; detected but inaccessible; confirmed absent; or availability unknown. Wait until availability and any actual application are known; do not announce an intention to use the skill and then announce its use again. Detection without application must never be reported as use. Keep the status out of project artifacts and do not repeat it in later replies.
For confirmed absence, combine a once-per-session installation suggestion with the status, linking https://github.com/blader/humanizer#installation and current host instructions. Respect an existing refusal. For unknown inventory or unavailable invocation, describe that limitation without claiming absence or successful use. On explicitly requests use but remains nonblocking when unavailable. Continue with baseline guidance in every fallback.
Never install/update skills, enable plugins, or modify global configuration automatically. Re-evaluate in a new session; no persistent machine-wide detection cache is required.
Apply the skill to all authored prose, including proposals, specs, tasks, guides, comments, docstrings, commit and PR descriptions, messages, and replies. Preserve code behavior, requirements, commands, identifiers, examples, links, and structured syntax. Check factual claims after rewriting; stylistic editing does not establish correctness. See the installed docs/configuration.md for defaults and limits.
