# Try a bounded prototype

Use a prototype when something concrete can resolve material uncertainty. First inspect available evidence and clarify questions that can be answered directly. Suggest an experiment only when a specific remaining question can change the solution. Users can also request one directly. Clear, understood work proceeds normally without a prototype, interview, or explanation for skipping them.

## Agree the experiment

Describe the question, expected learning, estimated effort, proposed workspace and outputs, meaningful time/resource limits, and the decision the result will inform. Clarify material missing limits. The user chooses whether to proceed. Reuse sufficient existing agreement within its scope instead of asking for the same permission again. If the user declines, continue ordinary clarification or planning and retain relevant uncertainty; do not create the prototype. Stop affected work and seek direction before materially expanding scope or resources.

Existing optional grill-me guidance applies. Suggest the interview when useful and use it on user request through exposed host capabilities. Neither availability nor an interview starts or authorizes a prototype. A prototype does not require the interview. If the skill is unavailable or declined, normal clarification remains available.

## Follow the native handoff

Native OpenSpec explore is read-only for code. Keep conversational sketches and read-only inspection there; name the supported change handoff and obtain any capture confirmation required by that workflow before writing experimental code or prototype files. Do not bypass explore's rules by calling the code temporary.

Recommend a short cliewen-discovery change for the agreed experiment before a separate delivery proposal. Use its existing proposal to state the question, limits, workspace, and decision criteria; run the bounded experiment during investigation and record its findings in investigation.md. A small experiment needs only a concise investigation proposal, not premature production specs or delivery tasks. If cliewen-all is explicitly selected, use its investigation and preserve its existing decision boundary before product implementation. Follow the selected workflow's native instructions and paths; add no new schema or prototype artifact prerequisite.

## Work within the agreed boundary

Use the agreed isolated experimental workspace, preferably an existing ignored project-local scratch location. Keep alternatives identifiable and label mock data, stubs, unsupported behavior, and checks honestly. Preserve production code, product acceptance tests, permanent specs, AC allocation, and capability mappings during investigation. Prototype checks establish observations about the experiment, not acceptance of unimplemented product behavior.

Describe actual isolation: an ignored directory or prompt instruction is not an OS-enforced sandbox. Existing project authority and external-action permissions still apply. Prototype agreement does not authorize production changes, purchases, installation, external access, or publication outside its described scope. Apply any permission already given to the required actions without redundant confirmation.

If a limit is reached, a check fails, or a measurement is invalid, record the actual outcome and what remains unknown. Do not report a stopped or unperformed experiment as successful. Reassess conclusions based on invalid measurements.

## Preserve findings and choose the next step

Use the existing investigation artifact to record method, inputs or revision, observations, actual user feedback and its source, agent interpretation, remaining uncertainty, and the next decision. Missing feedback is not positive feedback or approval. Distinguish supplied example feedback from a live user observation. Native investigation artifacts remain available even when optional documentation or planning is disabled.

With features.planning enabled, reference or update the selected planning authority using existing access and authorization; do not duplicate ticket status. When disabled, skip ticket access and plan maintenance and preserve authored files. With learnings.enabled and features.documentation enabled, follow the index-first learning policy and retain only useful reusable findings. Otherwise skip optional lesson maintenance. An experiment does not require a new decision record, lesson, or separate report when existing records suffice.

Use the findings to proceed, investigate further, choose an alternative, or stop. Record whether prototype code is discarded, retained as reference, or reviewed for further development. Respect the agreed cleanup scope and preserve authored work that should remain. Prototype code is not automatically production-ready.

If a delivery is selected, carry relevant findings and limits into its current proposal or the combined workflow's decision/specs. Review reused code and verify the actual delivery contract. Preserve existing approval and archive boundaries; an agreed experiment or positive result is not approval of a later production delivery.
