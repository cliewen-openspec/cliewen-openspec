## Configuration and workflow

Add independent `readiness.enabled` and `readiness.threshold` settings. Omitted values use `true` and `3` on existing and new installations regardless of setup profile. Accept integer thresholds from 2 through 4. A score of 1 describes a blocker. Preserve authored settings on update.

Put the rubric in the shared planning reference and call it from Delivery apply and the delivery branch of Combined. Use the completed scope review as input. Score the requested outcome and the ability to deliver and verify it separately. State a short reason for each score and compare the lower score with the threshold. Difficulty alone does not lower readiness. Enough evidence means the agent can proceed with existing authorization.

When the lower score is below threshold, use the request and available project evidence first. Pause only affected work. Ask the smallest consequential question when the user needs to decide. For technical uncertainty, use authorized discovery or propose a smaller delivery. Reassess when new evidence arrives. End the loop and report the blocker when further questions would add nothing.

## Ticket handoff

Follow the existing planning settings, authority, and permissions. Use the ticket to retain the blocking question, its impact, and the context needed to resume. Use the project's waiting convention when authorized. Re-read the ticket before adding a question or resuming. A retry reuses an outstanding question and only retries updates that are still missing. If an update fails or is unavailable, report the precise pending action. Local requests use the normal conversation or handoff.

Readiness is an agent assessment used alongside the existing review and approval rules. Keep ready cases brief and use an existing artifact or ticket only when a blocker needs to survive the session.
