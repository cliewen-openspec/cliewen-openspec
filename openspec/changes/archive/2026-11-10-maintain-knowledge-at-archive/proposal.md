# Proposal

## Why

A completed change can leave outdated explanations, unresolved test obligations, or future work based on assumptions the delivery disproved. Projects need a concise closure review around OpenSpec archive that preserves useful knowledge and accurately reports what finished.

## What Changes

- Supply one installed closure reference for delivery, discovery, and combined workflows, applying existing documentation, decision, learning, planning, and evidence settings.
- Review affected durable documents, decisions, test lifecycle obligations, useful enabled learnings, and unresolved work before archive.
- Offer an opt-in OpenSpec operation-guidance entry so an archive session can retrieve the reference even when it did not run implementation.
- After successful archive, report actual archive/sync results and reassess affected tickets or plan items under project completion criteria and existing authorization.
- Distinguish an archived change, ticket completion, Git integration, and current execution evidence in the handoff, including partial failures and pending updates.

The riskiest assumption is that schema instructions reach a separate archive session. A disposable OpenSpec 1.15.0 probe confirmed that operations.archive.guidance is returned by the native archive-input command with existing entries preserved. A supported operation entry pointing to a reference addresses that gap; an apply-only alternative would miss separate sessions. Test the published configuration example in a packed consumer and revise if it cannot retrieve the reference while retaining existing guidance. A checklist that merely produces more documents would fail the intended user, so retain only useful changes and a brief factual summary.

## Capabilities

### New Capabilities

- `change-closure`: Proportionate durable-knowledge review and accurate closure reporting around native OpenSpec archive.

### Modified Capabilities

None. Existing planning, learnings, quality/lifecycle, and evidence requirements remain authoritative; this capability composes their closure responsibilities.

## Impact

Shared apply instructions, one manifest-owned closure reference, installer ownership tests, user documentation, and unreleased changelog. Existing feature settings control the matching responsibilities. Projects opt in to native operation guidance by merging an example into their own OpenSpec configuration. No schema graph or report format changes are required.

Roadmap priority 2 in [the project plan](../../../../plan.md) owns this work. [Decision 023: Extend OpenSpec through its conventions](../../../../docs/decisions/023-openspec-native-planning-and-closure.md) establishes the design boundary. OpenSpec continues to own archive and synchronization; project policy governs approval, integration, and ticket completion.

## Approval

On November 10, 2026, the owner approved the proposal in the project conversation: "Ok. Vi tester om det virker efter implementering? Proposal er godkendt". Implementation and verification remain pending. Optional prototype exploration remains a separate future plan item; archive and publication require their own authorization.

## Implementation acceptance and archive

On November 10, 2026, the owner replied "go" to the recommendation to accept the review's documented limits and archive this change. Native OpenSpec archive completed on that date, adding five change-closure requirements to permanent specs. The combined trial's original learning-order deviation and the absence of a new observation after the approved guidance correction remain recorded. Publication was not part of this instruction.
